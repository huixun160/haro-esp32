



# **🔴 高优先级决策**







## **Q1 — 源码扫描深度**







### **✅ 选择：**

### **(A + C 组合，但以 A 为主，C 为补充)**







### **最终规则（必须执行）：**





> **优先扫描“公开接口层（export/include）”，只在必要时下探 source/**



------





### **为什么不是 (B) 深入 source**





因为你不是在 reverse engineer 整个平台实现细节，你是在做：



> **API/Capability建模 + 架构边界决策**



深入 source 会导致：



- 规模爆炸（数千 header + 内部函数）
- 把 HAL/internal 细节误当 API
- 工程师时间被吞掉，但决策质量不提升





------





### **正确扫描策略（非常关键）**







#### **Tier 1（必须扫）**





- export/
- include/
- 对外 header
- 文档中明确提到的 API





👉 这是“平台承认的能力边界”



------





#### **Tier 2（按需扫）**



仅在以下情况进入 source/：



- 文档中提到 API，但 header 不完整
- TM36 已识别 API，但 signature 缺失
- event/callback 只在 source 中定义
- 调用链断裂，需要补链





👉 这就是 (C) 的使用场景



------





### **一句话总结**





> **你不是在扫描代码库，你是在识别“平台暴露能力边界”。**



------





## **Q2 — 分阶段还是一次性完成**







### **✅ 选择：**

### **(B) TM-37a / 37b / 37c 分阶段**





------





### **为什么不能一次做完**





因为：



- 6 个模块 × 深扫 × completion = 高复杂系统任务
- 一次性做完 = 没有反馈循环
- 错了你会错一整轮





------





### **正确拆分（必须按这个来）**







#### **TM-37a（最关键）**





- UI / MMI
- Network
- Telephony





👉 这 3 个决定：



- app 架构
- 事件模型
- 网络调用模式





------





#### **TM-37b**





- Storage
- Device
- Audio





👉 决定：



- 数据持久化
- 输入输出
- 多媒体能力





------





#### **TM-37c**





- OS Core
- HAL / Peripheral
- Package / Download（见后面）





👉 决定：



- 系统底座
- adapter边界





------





### **一句话总结**





> **先搞清“app怎么活”，再搞清“系统怎么撑”。**



------





## **Q3 — E2E 路径验证**







### **✅ 选择：**

### **(A) + 轻量(B)，但不要求完整实现**





------





### **定义清楚（否则工程师会做错）**







#### **必须做（核心）**



👉 **调用链追踪（A）**

```
UI event
 → message loop
 → handler
 → network request
 → TCPIP
 → storage write
 → device feedback
```

必须能画出来 + 对应 API



------





#### **可选做（轻量验证）**



👉 **最小可运行验证（B-lite）**



- 不要求完整 app
- 只需验证关键链路“可打通”
- 可以是 demo / stub





------





### **❌ 不做的事情**





- 不要求完整功能实现
- 不要求 production 代码
- 不做 UI 完整交互





------





### **一句话总结**





> **证明“路径存在”，不是“产品完成”。**



------





# **🟡 中优先级决策**







## **Q4 — Package / Download 模块**







### **✅ 选择：**

### **(B) + 扩展（必须纳入）**





------





### **正确理解（很关键）**





这个模块不是 OTA/FOTA。



它是：



> **AIOS App 分发与安装能力**



包括：



- bin 下载
- 存储
- 校验（签名）
- 安装
- 卸载
- 版本管理





------





### **来源**





- DAP loader（已有）
- 下载能力（TCPIP）
- 存储（FS）
- 安全（你们已有加密）





------





### **为什么必须纳入**





因为你现在做的是：



> **应用商店 + 远程下发 bin**



如果这个模块不定义：



👉 你永远无法形成 app 生态



------





### **一句话总结**





> **这是你平台商业闭环的核心模块，不是可选项。**



------





## **Q5 — 完成度等级定义**







### **✅ 选择：**

### **(A) 严格：6/6 才算 complete**





------





### **为什么不能选 B / C**





因为你现在处在：



> **架构决策前最后一层数据准备**



如果你允许：



- 没 event
- 没 dependency
- 没调用链





你做出来的 Service 划分一定是错的。



------





### **6 条必须全部满足：**





1. 模块职责
2. capability
3. API
4. event/callback
5. dependency
6. layer tag





------





### **允许的唯一例外**





可以标记：

```
completion_status: partial
missing:
  - event
  - dependency
```

但：



> ❗ partial 模块禁止进入 TM38 决策



------





### **一句话总结**





> **你现在要的是“决策级数据”，不是“差不多”。**
